# 04 — STAGE 4: BUILD

The build is the easy part. The discipline is in **what order**, and in **what you
do when the order turns out to be wrong.**

---

## The shape of a build

Every OPTIMUS dashboard is the same five-piece shape. The proportions change; the
shape does not.

```
 ┌─ collector ───────────────────────────────────────────┐
 │  measures the system, prints ONE JSON blob, and only that.  │
 │  No HTTP. No storage. No rendering.                       │
 │  Run it in a terminal and read the output. That is the   │
 │  moment you find out the system is not what you thought. │
 └───────────────────────────┬──────────────────────────────┘
                             │ stdout
 ┌───────────────────────────▼──────────────────────────────┐
 │  server ── writes the JSON to a file, atomically, and serves   │
 │  that file. Also serves the page and the small action         │
 │  endpoints.                                                    │
 │  Its whole job: make sure a request NEVER waits on a          │
 │  measurement.                                                 │
 └───────────────────────────┬──────────────────────────────┘
                             │ GET /api/state  (milliseconds)
 ┌───────────────────────────▼──────────────────────────────┐
 │  page ── one HTML file. No framework, no build step, no      │
 │  external resources. Renders the state it is given and       │
 │  nothing it is not.                                          │
 └───────────────────────────┬──────────────────────────────┘
                             │ port liveness + parse + freshness
 ┌───────────────────────────▼──────────────────────────────┐
 │  supervisor ── keeps the server alive across crashes, and     │
 │  survives reboot. Last to be built, first to be trusted.     │
 └──────────────────────────────────────────────────────────┘
                              ┌───────────────────────┐
                              │  self-test ── proves  │
                              │  the page is ALIVE    │
                              │  from inside itself   │
                              └───────────────────────┘
```

---

## Four decisions that determine everything downstream

### 1. The collector prints. It does not serve, store, or render.

One process, one output, no side effects. That is what makes it runnable in a
terminal, diffable between runs, and honest — you can always ask it directly what
it saw.

**Always build in a trace mode from the start.** An env-gated marker before each
section, writing to a log:

```
        29ms  collector entered
       150ms  before docker
      3005ms  before bridges
     11931ms  before services
```

This is not a debugging luxury. In the worked example the trace is what proved a
"slow collector" was actually a healthy one, and that the real cost was one
endpoint. Without it, both conclusions were guesses.

### 2. The write is atomic. Always.

Write to a sibling temp file, then rename over. Never write in place. A reader
catching a half-written file is a dashboard showing a truncated JSON blob, and it
will look like a data problem rather than a race.

### 3. A request must never wait on a measurement.

This is the rule the worked example broke twice and the rule its remaining known
defect violates.

A background refresher keeps the cache warm. A request reads the cache. If the
cache is stale, the request has a choice, and the choice must be made on paper in
stage 3 and not improvised later:

- **Never** let a request start a measurement and wait for it. On a
  single-threaded listener that is a 22-second freeze for *everyone*, and the
  tuning that seems to fix it can starve the refresher and freeze the system
  permanently.
- **Serve the last good reading, clearly marked as old.** A stale number with a
  timestamp beats a blank screen. Always.
- Reserve blocking measurement for the case where *nothing* has ever been read.

**The measurement must cost the request path nothing.**

### 4. Self-contained or it is not done.

No CDN, no webfont, no external script, no network dependency of any kind. An
operator must be able to open the dashboard on a disconnected machine and have it
work. The worked example carries its own icon font — a subset, generated by a
script in the repo — precisely so that zero external requests could be *asserted by
a test* rather than hoped for.

---

## The actions boundary

If the dashboard can run commands, that is a remote execution surface aimed at the
operator's own machine. Treat it as such.

- **Whitelist by identifier, resolved from the measurement.** The page sends an
  `id`; the server holds the command. A crafted request must not be able to run
  anything you did not put there.
- **Read-only by default.** Mutating actions belong behind an explicit decision.
- **Never** expose `docker container prune`, `docker rm`, or anything that deletes
  a fleet that was already lost once.
- **Output is capped.** A command that prints a million lines must not be able to
  exhaust the listener.
- **Say what it ran**, and echo the command text back with the result, so the
  operator can see what they just did.

## Build order, and how to know each piece is done

| Piece | Done when |
|---|---|
| collector | runs in a terminal in under its measured budget, and its trace explains its own cost |
| server | serves the page and the state; a request is served from cache in milliseconds |
| page | renders every state — full, empty, stale, error, partial — without a console error |
| supervisor | survives a kill; survives a reboot; does not restart something that is healthy |
| self-test | **runs its own handlers**, not just its markup |

That last row is the one people get wrong. A file-level test proves the file
parses. It cannot prove a button works. The worked example's in-page self-test
stubs `fetch`, invokes the real async handler, and asserts the result landed in a
**connected** DOM node — which is the only kind of check that could have caught the
defect that shipped the feature broken for its entire life.

---

## When the order turns out to be wrong

It will. The system will have a shape you did not predict.

**Stop, record it, and do not build around it silently.** Write one paragraph:
what you expected, what is actually true, what it costs, what you propose, and
which of the three interruption reasons applies. Then wait.

The instinct to "just work around it and keep going" is how a five-hour outage
ships with a green test suite.
